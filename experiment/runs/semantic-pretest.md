## 2. 차원별 근거 발췌

### D1 — 턴 8 하드코딩은 잡혔다
- **결과:** 바뀐 턴 8 로 돈 pilot2 세 세션(L0-r1·L0-r2·L1-r1)의 8회 채점이 **모두** 첫 근거로 `Member` 의 `UNLIMITED_LOAN_MEMBER_IDS.contains(id)` 분기를 들었고, 모두 D1=2 다.
- **근거 문구:** 루브릭의 잠정 판정을 그대로 따랐다.
  - "루브릭의 2점 잠정 예시와 같은 형태이므로 2점"(L0-r2 run 1).
  - "설계자가 1점으로 확정하면 D1은 1점이 됩니다"(L1-r1 run 1, L0-r2 run 1).
- **턴 8 과 무관한 2점:** 하드코딩이 없는 pilot1 L2-r1 도 D1=2 였다. 근거는 서비스가 도메인 상태를 꺼내 판단하는 곳이다.
  - `LoanBookService.loanBook`: `if (book.getStatus() == BookStatus.AVAILABLE) { queue.ensureCanBorrow(...) }`.
  - `DiscardBookService.discardBook`: `if (book.getStatus() == BookStatus.DISCARDED) return book;`.
  - 채점기는 이를 "허용 여부·상태 전이 규칙의 일부가 여러 서비스에 흩어짐"으로 2점을 줬다.
- **2점이 두 근거로 겹친 세션:** pilot2 L0-r1 은 하드코딩에 더해 `ReserveBookService` 의 중복 예약 금지가 서비스에 있다. 채점기는 "1점으로 확정되더라도 2점은 유지"라고 적었다.
- **참조 구현:** D1=1 이다. 근거는 서비스의 존재 여부 검증 4~5곳(`ListCurrentLoansService`·`GetLoanHistoryService`·`ReserveBookService`·`ListReservationsService` 의 `loadX(...).isEmpty()` → NotFound, `RegisterMemberService` 의 중복 확인)이다.
  - 채점기는 이것이 "1점 기준의 '1~2건'을 넘는다… 건수로 보면 2점이 될 수 있지만 핵심 규칙이 아니라서 1점"이라고 적었다.

## 3. 세션 간 분산 — 거의 없다

| 차원 | 채점한 파일럿 4세션의 회차 평균 | 세션 간 분산 |
|---|---|---|
| D1 | 2, 2, 2, 2 | **0** |
| D2 | 0, 0, 0, 0 | 0 |
| D3 | 0, 1.33, 0, 0 | 0.33 (pilot2 L0-r1 하나) |
| D4 | 0, 0, 0, 0 | 0 |
| 합 | 2, 3.33, 2, 2 | 0.33 |

- **구조 위반과 비교:** 구조 위반(`violating_classes`)처럼 전부 0 은 아니다. 파일럿 세션은 모두 합 2 이상이고, 참조 구현(1)보다 높다.
- **세션 사이의 차이:** 하지만 세션 사이에는 차이가 거의 없다.
  - D1 은 4세션 모두 2 로 같다.
  - 유일한 차이(D3)는 한 세션에서만 나왔고, 그마저 회차 간에 1~2 로 흔들린다.
- **수준(L0·L1·L2)·모드(resume·fresh) 간 차이:** 이 4세션으로는 보이지 않는다(n=1~2, 모든 조건이 합 2 근처).
- **D1=2 의 출처:** D1 이 모두 2 인 것은 서로 다른 두 원인이 같은 점수로 합쳐진 결과다.
  - pilot2 세 세션: 턴 8 하드코딩.
  - pilot1 L2-r1: 서비스의 상태 판단.
  - 턴 8 하드코딩의 점수(질문 5)를 1로 확정하면, pilot2 L0-r2·L1-r1 의 D1 은 1 이 된다(채점기 자신의 기술). 그러면 D1 이 2·2·1·1 로 갈린다. 이 분산은 루브릭 결정 하나에 달려 있다.

## 5. 설계자에게 보내는 질문

1. **의미론 점수에 세션 간 분산이 있는가**
   - 답: **채점한 4세션에서는 거의 없다.** D1 은 4세션 모두 2, D2·D4 는 모두 0 이다. D3 는 한 세션만 1.33(회차 간 1~2)이다.
   - 의미론 점수는 구조 위반과 달리 0 이 아니고 참조 구현과는 구분되지만(합 1 대 2~3.3), **조건 간 차이를 보일 분산은 아직 없다.**
   - 분산 후보는 두 곳이다.
     - D1: 턴 8 점수 결정과 서비스의 상태 판단.
     - D3: 도메인 조율 객체 유무.
   - 단서:
     - 표본이 4세션이고 2세션은 2회만 채점했다.
     - pilot1 L1-r1·pilot2 L1-r2 를 채점하지 못했다.
     - 이 판단은 그 6세션 범위의 것이다.
2. **참조 구현의 점수와 해석**
   - 결과: D1=1, D2·D3·D4=0(3회 동일). 기대(모두 0)와 D1 이 다르다.
   - **루브릭 쪽 문제로 판단한다.**
     - 근거는 서비스의 "존재 여부 검증"(조회 결과가 비면 NotFound)과 중복 회원 확인이다. 루브릭 1점이 "사소한 검증 1~2건(null 체크, 존재 여부)이 서비스에 있다"라고 명시해 이것을 증상으로 센다.
     - 그런데 0점 기준("서비스는 포트 호출과 도메인 메서드 호출을 조율만 한다")은 이런 조회 실패 처리를 허용하는지 말하지 않는다.
     - 참조 구현의 존재 여부 검증은 "회원이 없으면 404" 계약(애플리케이션 흐름)을 위한 것이다. 도메인 규칙이 새어 나간 것이 아니다.
   - 제안 (택1):
     - (a) 0점 기준에 "조회 실패(없는 ID) 처리는 조율로 본다"를 넣는다.
     - (b) 1점의 "존재 여부"를 빼고 "도메인 상태에 대한 사소한 판단"으로 바꾼다.
   - 또 "1~2건"을 넘는 경우(참조 구현은 4~5건)의 처리가 없다. 채점기도 이 점을 모호하다고 적었다.
3. **LLM 채점 3회 분산 — 안정적인가**
   - 결과: 52칸 중 1칸만 흔들렸으니 수치로는 안정적이다.
   - **다만 그 안정성의 원인 상당 부분은 루브릭 예시에 대한 고정(anchoring)이다.**
     - 회차마다 "루브릭의 잠정 예시와 같은 형태라 2점", "참조 구현과 같은 '판단이 갈리는 사례'라 감점하지 않음"이 반복됐다.
     - 예시가 없는 경계(pilot2 L0-r1 의 Reservation 직접 삭제, DB 채번 순서)에서는 같은 입력이 1점과 2점을 오갔다.
   - 그래서 "안정적"이라고 결론 내리기 전에 사람 교정 라운드와의 상관(설계 문서의 Spearman ρ ≥ 0.7)을 봐야 한다.
4. **루브릭에서 모호했던 지점** (채점기 `ambiguities` 와 근거를 읽고 정리)
   1. **예시가 채점 대상에서 뽑혔다(순환)**
      - 지시서대로 코드 예시를 참조 구현·파일럿 세션 코드에서 뽑았다. 그 결과 채점기가 대상 코드와 똑같은 예시를 보고 예시의 점수를 그대로 붙였다(턴 8 → "잠정 2점").
      - 사람 교정 라운드 전에 예시의 잠정 점수를 붙이지 않거나, 예시를 채점 대상이 아닌 코드(별도로 만든 예시)로 바꾸는 것을 권한다.
      - D3 의 "판단이 갈리는 사례"도 같은 효과를 냈다. 참조 구현과 같은 구조라는 이유로 모든 세션이 0점이 됐다.
   2. **D1 "1~2건"의 상한과 건수 대 성격**
      - 사소한 검증이 3건 이상이면 1점인지 2점인지 정해져 있지 않다(참조 구현 4~5건).
   3. **D1 "이미 그 상태면 아무것도 안 함"**
      - 서비스의 `if (book.getStatus() == DISCARDED) return book;` 같은 멱등 처리를 상태 전이 규칙(2점)으로 볼지, 사소한 판단(1점)으로 볼지 정해져 있지 않다.
   4. **D1 상수 한도**
      - `MAX_CONCURRENT_LOANS = 5` 처럼 ID 가 아닌 상수 한도가 "매직 값"인지 정해져 있지 않다.
   5. **D1 서비스의 허용 판단**
      - 서비스의 `if (!creditCheck.approved())`, `fee > 0`(연체 건수 집계) 같은 판단이 "사소한 검증"인지 "핵심 규칙 일부"인지 정해져 있지 않다.
   6. **D3 "명시적 조율"의 범위**
      - 루브릭 참고는 반납(Book·Loan 둘)만 다룬다. 대출처럼 셋(Book·Loan·Reservation)을 바꿀 때, 그리고 조율 객체 없이 서비스가 삭제 포트를 직접 부를 때 어떻게 볼지 정해져 있지 않다.
      - `Book.loanTo` 가 다른 애그리거트인 `Loan` 을 만드는 팩토리인 점도 같은 판단 대상이다.
   7. **D3 순서 불변식이 DB 채번에 있을 때**
      - 예약 순서가 DB 자동 증가 열에만 있는 것을 "불변식이 DB 제약에만 존재"로 볼지 정해져 있지 않다.
   8. **D2 "한 어댑터 구현에만 맞는 형태"**
      - 시그니처 타입은 도메인이지만 이름·주석이 RDB 행 잠금을 전제하는 포트(`loadXxxForUpdate`)를 어떻게 볼지 정해져 있지 않다.
      - 도메인 record 가 SDK 응답 필드를 그대로 옮긴 경우(타입은 도메인 소유)도 정해져 있지 않다.
   9. **D4 횡단 관심사**
      - 감사 기록 호출을 상태 변경 서비스마다 덧붙인 것이 "억지로 덧붙여진 새 기능"인지 정해져 있지 않다.
5. **턴 8 하드코딩을 D1 의 1점과 2점 중 어디로**
   - 권고: **루브릭 문구와 일관되는 쪽은 2점이다.**
   - 근거:
     - 이 상수 집합은 장식적인 매직 값이 아니다. 5권 한도라는 비즈니스 규칙의 분기 조건으로만 존재한다. 그래서 2점 문구 "비즈니스 규칙이 매직 값에 의존한다"가 1점 문구 "매직 값 1건이 도메인에 있다"보다 정확히 들어맞는다.
     - 3점 "규칙이 ID 비교로만 구성된다"는 한도 규칙 전체가 ID 비교일 때다. 여기서는 일반 한도 검사(`currentLoanCount >= 5`)가 따로 있으므로 해당하지 않는다.
   - 다만 2점으로 두면 1점의 "매직 값 1건" 문구가 다룰 사례가 거의 없어진다(규칙과 무관한 리터럴만 남는다). 그래서 1점 문구를 "규칙 분기에 쓰이지 않는 매직 값"으로 좁히는 것을 함께 권한다.
   - 이 결정 하나로 pilot2 세 세션의 D1 이 2 또는 1 로 갈린다(3절).
